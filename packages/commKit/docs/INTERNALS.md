# CommKit Internals

This document describes implementation invariants for maintainers. It is not an additional public API; the contract and the wire protocol are in [`API.md`](API.md).

## Package state

`CommKit._state` is shared by every embedded copy and kept across upgrades:

| Field | Meaning |
|---|---|
| `schema`, `runtimeRevision` | The state layout (1) and the revision that last committed its functions. |
| `dispatch` | Every function another Kit calls back into, by name. |
| `trampolines` | The closures handed to EventKit, TimerKit, SchedulerKit and HookKit, created once per session; each only looks its target up in `dispatch`. `logout` (revision 2) calls `dispatch.closeAddonScopesAtLogout`. |
| `metatables` | One metatable per object kind (`scope`, `connection`, `handle`, `syncSet`), whose `__index` is the shared prototype. |
| `addonScopes` | Addon name to canonical scope. Only `CloseAddonScopes` closes one, called by LifecycleKit, by CommKit's `OnShutdown` subscription or by its `PLAYER_LOGOUT` watcher ("At logout" in `API.md`); a closed scope stays in the map, so closing is terminal and the map grows only with `ForAddon` calls. Each scope carries `_logoutCloser` (`false` for a manual scope, else `"lifecycleKit"`, `"onShutdown"`, `"playerLogout"` or `"none"`) and `_shutdownSubscription` (the case (b) subscription or `false`, disconnected by `closeScope`); they are scope layout 2, and an upgrade over revision 1 adds them to every addon scope and arranges the open ones. |
| `limits`, `statistics` | The shared limits and counters. |
| `queues` | Per priority: `ring` (pipes in service order), `cursor` (the next pipe), `pipes` (key to pipe), `messages`, `bytes`. |
| `blockedPipes` | Pipes set aside after a throttle, waiting for `blockedUntil`. |
| `queuedMessages`, `queuedBytes`, `rotationCursor`, `nextStreamId`, `nextLoggedStreamId` | Queue totals (aborts included, at zero bytes), the priority rotation's position, the id after the last stream started in each digit scheme. |
| `inFlightStreams`, `inFlightBytes` | Streams receivers may hold from this client: multi-chunk messages whose first chunk left and last did not, and aborts not yet sent; and the bytes their first chunks declared. |
| `syncReplyBytes` | Text bytes of SyncSet replies in the queue. |
| `budget` | `tokens`, `lastRefill`, `zoningUntil`, `framesPerSecond` (the last sample, or `false`), `sampledAt` (when it was taken, or `false`; revision 6). |
| `driver` | `job` (the armed driver run, a SchedulerKit job or, without SchedulerKit, a TimerKit timer, from revision 11; or `false`), `delayed` (what it waits for: `false`, `"budget"`, `"blocked"`, `"frame"`, `"retry"`, or `"callbacks"` for a job that only makes held callbacks while the queue is empty), `sampler` (the frame-rate ticker or `false`; started by a run that leaves something queued, from revision 5), `running` (a run is on the stack), `inline` (that run is one `Send` makes on its caller's stack; revision 6). |
| `deferred` | Revision 6: the progress and completion calls a run inside `Send` held back. `count` calls are stored in the array part, four slots each (callback, handle, and the two values; `false` stands for a `nil` reason), `cursor` of them made; `flushing` counts the passes on the stack. |
| `sendingOwnTraffic`, `outsideHooks`, `outsideLookupAt` | The re-entrancy flag, the HookKit scope holding the outside-traffic hooks (`false` until installed), and when HookKit was last looked up while none was installed (`false` before the first lookup; revision 7). |
| `streams`, `streamList`, `senders` | Open streams by key and in opening order; per sender, `{ streams, bytes }`. |
| `expiry` | `timer` (the armed expiry timer or `false`), `due`, and `idleTimer` (revision 5): the one-shot TimerKit timer, created with `New` for the current `reassemblyTimeout`, that `armExpiry` restarts whenever it arms a full timeout; an earlier deadline gets a plain `After` timer. `false` until first needed, and replaced when the timeout changed or its scope was closed. |
| `dropReports` | `bySender` (sender to `{ reportedAt, pending, reasons }`), `count`, and the one flush timer and its due time. |
| `prefixSignals`, `prefixCounts`, `clientPrefixes`, `registrationTotal`, `chatConnections` | Per prefix, the SignalKit signal and the live registration count; prefixes registered with the client; the total; the EventKit connections for the chat and roster events. |
| `prefixFraming` | Revision 8: per prefix with a live registration, `"framed"` (`Register`, `SyncSet`) or `"raw"` (`RegisterRaw`); set by `registerInScope`, cleared by `disconnectConnection` with the prefix's last registration. An upgrade over revision 7 builds it with every registered prefix framed. |
| `kitScopes` | CommKit's own EventKit, TimerKit and SchedulerKit scopes, the `PLAYER_ENTERING_WORLD` connection, and `logout`, the one `PLAYER_LOGOUT` `Once` connection of case (c), or `false` (revision 2; an upgrade over revision 1 adds it). |
| `pools` | PoolKit table pools: `streams` (reassembly), and in an inherited state `records` (the queue records revision 5 and earlier leased; revision 6 only returns them) and, from revision 4 or earlier, `parts` (the separate chunk lists those revisions leased; revision 5 only returns them). A new state creates neither. |
| `parts`, `helpers`, `partInterface`, `transports` | Revision 11, the part interface (ADR 0001): part name to its record (`{ revision = n }`, plus the ChatThrottle part's `battleNetConnection`), the core functions a part calls by name (refilled by every core that loads, so a part reads the newest core's helpers at call time), the generation of `helpers` (1), and the senders of pipes a part fills (`chat`, `battleNet`). An upgrade over a whole-file revision adds them empty and arms the next-frame check of inherited SyncSets (see [Callbacks and upgrades](#callbacks-and-upgrades)). |
| `spares` | Free lists: `pipes` (emptied pipes, their FIFO kept) and `senders` (per-sender `{ streams, bytes }` records), each at most `POOL_RETAINED.spares` (16) long (revision 5), and `records` (finished queue records), at most `POOL_RETAINED.records` (64) (revision 6). An upgrade adds the lists an older state lacks, empty. |

## Sending

A **record** holds one queued message: its handle, scope, prefix, text, destination, priority, pipe, chunk count, next chunk index, bytes sent, stream id (`false` until its first chunk is built) and callbacks. The **handle** is a separate small table the caller keeps; it holds the state and the byte counts and points at the record until the message is terminal. `completeSend` is the only way out of the queue for a message: it dequeues the record, settles the handle, removes it from the scope's `_pending`, releases the record, disarms the driver when that emptied the queue outside a run, and only then calls `onComplete` through `deferCallback`.

**Records** come from `acquireRecord` and go back through `releaseRecord` (revision 6): a record CommKit built carries `freeListed = true`, is stripped of its text, handle, scope, callbacks and pipe, and kept on `spares.records` up to 64; one without the mark was leased from a revision 5 copy's PoolKit pool and goes back there. PoolKit's generic lease and reset took about a tenth of a short send's time on the host; every field a record is read for is set when it is acquired (`enqueueSend`, `queueAbort`), so clearing only the references is enough.

**Held callbacks** (revision 6). `deferCallback` is the only way a progress or completion callback is called. During a run inside `Send` (`driver.inline`) it appends the call to `deferred`; otherwise it first makes every held call (`flushDeferred`), then the call, so a handle's calls keep their order whatever completes it. `flushDeferred` advances `cursor` before each call and makes calls appended during the pass in the same pass, so a `Cancel` inside a held callback nests safely; each call runs under `pcall` around `isolatedCall`, so a host whose `securecallfunction` lets an error escape cannot leave `flushing` raised. `runDriver` flushes before it sends, with `running` set, so a send from a held callback queues and leaves in that run.

A **raw record** (revision 8, `scope:SendRaw`) is of kind `"raw"`: `parts` holds the caller's addon messages (a copy), `text` is `false`, `textLength` the parts' bytes and `totalChunks` their count, and `logged` is always `false`. `buildChunk` returns `parts[nextIndex]` as it is; `headMayStart` always lets it start, `assignStreamId` skips it and `acceptChunk` takes no in-flight allowance for it, so it never holds a stream id and `completeSend` never queues an abort for it. `releaseRecord` lets go of `parts` with the other references.

An **abort** is a record of kind `"abort"` with no handle, scope, text or callbacks: `completeSend` queues one at the head of the pipe when a message is cancelled or fails after its first chunk left, and `finishAbort` releases it once sent or refused. A started message holds an in-flight allowance (`inFlight`); `completeSend` releases it when the message is sent; on a cancellation or a failure the abort takes it over until `finishAbort`, because receivers hold the stream until the abort arrives. `headMayStart` keeps a multi-chunk head that has not started waiting while the allowance is spent. `SetLimits` fails a message that has not started and that declares more than a lowered `maxReassemblyBytesPerSender`, so no head waits forever.

**Stream ids.** `assignStreamId` gives a multi-chunk head its id each time its first chunk is built: the scheme's counter, skipped past any id an in-flight head (a started message or an abort, always the head of its pipe) holds. The counter moves past the id only when the first chunk is accepted. In-flight streams number at most `maxInFlightPerSender` (at most 64), below both radixes, so a free id always exists.

A **pipe** is `{ key, priority, fifo, blocked, blockedUntil, backoff }`. It lives in its queue's `ring` or, while blocked, in `blockedPipes`, and in `pipes` either way, so a send to a blocked destination joins the blocked pipe. An emptied pipe is forgotten at once: `removePipe` takes it out of every structure and puts the table on `spares.pipes`, and `obtainPipe` resets a spare to a new pipe's fields (its FIFO is already empty) before it builds one. Forgetting stays immediate, so a destination's throttle backoff is not remembered past its last message, as before revision 5.

### Driver

**Where a run is armed** (revision 11). `armDriverRun(kind, delay)` arms the one run: a job in CommKit's SchedulerKit scope while SchedulerKit is loaded (`Schedule` for `"ready"`, `NextFrame` for `"frame"`, `After` for `"after"`), and otherwise a timer in CommKit's TimerKit scope (`After(0)` for `"ready"` and `"frame"`, `After(delay)` for `"after"`). The rest of the driver only stores the handle and calls `Cancel()` on it, which both kinds answer, so a job an older revision scheduled is taken over unchanged. SchedulerKit is found with `Registry:Find`; a facade once found is kept in the block (Registry hands every compatible revision the same table), and until one is found the lookup runs at most once per `POLICY.schedulerLookupSeconds` (1 s), as the HookKit lookup does, since a busy driver arms often. The diagram below says `After`, `NextFrame` and `Schedule`; without SchedulerKit read them as the TimerKit timers above.

```text
idle ──Send──→ run inside Send ──→ sends chunks, holds their callbacks
  ↑                                     │
  │      busy ──Send──→ queued; the next run serves it
  │                                     │
  │  scheduled ←── After(wait) ←─ bucket short ("budget")
  │  scheduled ←── After(until) ←─ only blocked pipes left ("blocked")
  │  scheduled ←── NextFrame ←──── 32 chunks this run ("frame")
  │  scheduled ←── Schedule ←───── callbacks held ("callbacks", or false
  │                                while something is queued)
  │      │
  │      └──run──→ makes held callbacks, then sends chunks
  │                                     │
  └──────────────── queue empty, nothing held (sampler stopped)
```

`SendPath.sendAtOnce` (revision 10) comes before both: a message of one chunk with no callbacks, while nothing is queued, no run is on the stack and no job is scheduled, gets one bucket check (`refill` and the driver's affordability test inline, with one `currentMode` reading) and one protected client call with `sendingOwnTraffic` set. A sent chunk charges the bucket and counts `chunksSent`, `bytesSent`, `messagesQueued` and `messagesSent` as `acceptChunk` and `completeSend` would, and the handle is built already `sent`, with no record, pipe or run. A throttle, a refusal or a raise returns the outcome to `enqueueSend`, which enqueues the record as usual and then does what `driveChunks` does with that outcome (`setPipeAside` and `finishRun` for a throttle, `completeSend` failed otherwise), so the client is never asked twice inside one `Send`. No pipe and no record exist while the queue is empty, so the rotation, backoff and stream ids have nothing to decide.

`runInline` (revision 6) is the run `Send` makes when the driver is idle: no run on the stack (`running`), no pass over held callbacks (`deferred.flushing`), and no job but a `"callbacks"` one. It does what a wake from idle does (a frame-rate sample at most once a second, the outside-traffic hooks), sets `running` and `inline` around a protected call of `driveChunks`, and afterwards, when callbacks are held and no run is due on the next frame, replaces whatever job it left (a bucket or backoff wait) with an immediate `Schedule` job, so held callbacks never wait for the bucket. `stopDriver` keeps the job while callbacks are held, because that job makes them. Otherwise `enqueueSend` calls `wakeDriver`.

`runDriver` sets `running` around a protected call of `flushDeferred` (when calls are held) and one of `driveChunks`, and afterwards starts the frame-rate ticker if the run left something queued (`wakeDriver` only samples once): a message the first run sends in full never builds a ticker, and a longer one gets it at most one frame later than the wake, which the ticker's one-second period does not notice; while it is set, `wakeDriver` schedules nothing, so a send from a progress or completion callback never schedules a second job: the run serves it or `finishRun` arranges the next run. `scheduleDriver` cancels any job it replaces. Otherwise `wakeDriver` schedules a run unless one is coming; a run waiting only for a blocked pipe is cancelled and replaced, because the new message may use another pipe. `stopDriver` cancels the job and the sampler; `finishRun` calls it when the queue is empty, `completeSend` when a cancellation empties it outside a run, and `runDriver` when a failed run left nothing queued (with something queued, it retries a second later). `peekNextPipe` finds the next pipe without moving a cursor; the cursors move only when a chunk is handed to the client, so a chunk the bucket cannot pay for is the one tried next. The bucket check in `driveChunks` (revision 10 computes it inline, with the mode and rate read once per run; earlier revisions called `secondsUntilAffordable`) rounds a deficit under one byte to zero and caps the requirement at the capacity; both prevent a run from waiting forever or re-arming nanosecond timers.

**Pipes a part fills** (revision 11). A record carries `transport`: `false` for addon messages, or the name of a sender in `state.transports`. `driveChunks` picks that sender instead of `SendAddonMessage`, and `transmit` calls it as `sender(record, chunk)` inside the own-traffic flag; the sender makes the client call and returns its result, which `classifySendResult` reads as for addon messages (`nil` means sent, which is all `SendChatMessage` answers). `SendPath.enqueueTransport` builds such a record (a `"raw"` one for a chat line, one part; a framed `"message"` for Battle.net, on the logged digit scheme) with the queue's bounds and refusals, and `SendPath.sendOutsideQueue` sends a hardware-event chat line now or not at all: refill, the driver's affordability test, the client call, the statistics, a terminal handle, and the completion callback held as a run inside `Send` holds it (with a `"callbacks"` run armed when none is). Battle.net registrations are keyed `prefix` followed by 17 NULs and `battleNet`, longer than any realm prefix, so the core's prefix signals, framing and reassembly keep them apart; the sender key is `"\0battleNet\0"` and the game account's digits, and the distribution `BATTLE_NET`, so roster eviction never touches them. `registerInScope` takes the prefix to register with the client separately (`clientPrefix`), and `GetPrefix` answers `_publicPrefix` when a registration carries one.

**The outside-traffic hooks** (revision 7). `installOutsideHooks` runs on every wake from idle (`wakeDriver`, `runInline`) and returns at once once `outsideHooks` holds a scope. Until then it looks HookKit up with `Registry:Find` only when `outsideLookupAt` is `false` or at least `POLICY.hookLookupSeconds` (1 s) old, and records the time of each lookup, found or not. It takes the clock reading `sampleFrameRate` made for the same wake, so the gate costs no extra `GetTimePreciseSec` call. Revision 6 looked HookKit up on every wake, about a tenth of a short send's time on a session without HookKit; the rate limit moves the promise in `docs/API.md` ("Traffic CommKit did not send") from "the first wake after HookKit is found" to "the first wake at least one second after the previous lookup".

## Receiving

`onAddonMessage` checks every argument's type and secrecy before using the prefix as a key, returns at once for a prefix nobody registered, delivers the whole text to a raw prefix (`prefixFraming`, revision 8) without reading its first byte, and delivers a single chunk with one `string.sub`. Multi-chunk keys are `prefix \t distribution \t sender \t streamId`. The key's last part comes from `WIRE.plain.keySuffix` or `WIRE.logged.keySuffix`: the scheme's `keyMarker` and the id, made the first time an id is received and kept (revision 10; before, every one was built at load, 19.2 KB a session held whether it received anything or not), because a number in a concatenation is formatted with `sprintf` on every chunk; the keys are the ones every revision writes. A stream record (pooled) holds the key, the four identifying strings, `total`, `received`, the byte `reserved` against its sender and the `deadline`, and, from revision 5, the chunk payloads in its own array part by chunk number (a stream a revision 4 copy opened keeps them in a pooled `parts` list, which `continueStream` and `closeStream` still read and release). Per-sender records come from and return to `spares.senders`. `closeStream` is the only way out: it unlinks the stream from all three structures (the oldest stream, the usual case, without a search), releases what it leased, and cancels the expiry timer when no stream is left; `dropStream` adds the counter and, except for an abort, `noteDrop`. `noteDrop` reports a sender's first drop at once and accumulates the rest until `flushDropReports`, on one TimerKit timer, reports them a minute later; entries with nothing pending are forgotten after their minute. Keys include the channel (`\tlogged\t`), and headers are decoded with the digit scheme of the event that delivered them; the `CHAT_MSG_ADDON` trampoline passes on only the four arguments CommKit reads.

## Callbacks and upgrades

Registrations and `OnChanged` listeners are SignalKit connections whose listener closes over the consumer's callback and calls `dispatch.isolatedCall`, so errors are isolated per listener while SignalKit keeps ordering and mutation-during-dispatch semantics. The SyncSet's own registration closes over the SyncSet and calls `dispatch.receiveSync`, which the SyncSet part fills. Because every closure CommKit hands out resolves its behaviour through `dispatch`, a newer revision needs only to rewrite `dispatch` and the prototypes; objects and queued work carry over untouched.

**Parts** (revision 11). A part resolves the core with `Registry:Find("commKit", 1)`, checks `parts`, `helpers` and `partInterface`, and returns at once when an equal or higher revision of itself is installed. It writes its methods onto the shared prototypes, its hooks into `dispatch` (`receiveSync`; the ChatThrottle part's `onBattleNetMessage`, `chargeOutsideBattleNet`, `installPartHooks`) and its senders into `transports`, and records itself in `parts`. The core writes a stub for every member of a part that is not in `parts` (`Parts.installStubs`), never over an installed part's member, so a newer core loaded after a part keeps the part's methods. A part reads core functions through `helpers.<name>(...)` at the call, so a validator's explicit error level counts exactly as it did when the code lived in the core. The core keeps `closeSyncSet`: a scope's `UnregisterAll`, `Close` and logout close SyncSets whether or not the part is loaded.

**Over a whole-file revision.** A state built by revision 10 or older may hold SyncSets whose part is not loaded yet: the part, when an addon embeds it, loads right after the core. The core therefore arms a zero-delay timer that runs `dispatch.checkInheritedSyncSets` on the next frame. When the SyncSet part is installed by then, nothing happens. Otherwise the SyncSets of addon scopes (`addonScopes`) are closed, `dispatch.receiveSync` becomes a function that reports once, and that report names the file to embed; a manual scope's SyncSet cannot be found from the state, so it stays registered but inert (its methods are stubs) until its scope closes it.

## Hot paths

The send path, the driver and the receive path index CommKit's own tables (the state and its sub-tables, queue records, pipes, stream records, the limits and the counters) with plain field access. None of them has a metatable, so this reads and writes exactly what `rawget` and `rawset` would, without a C call each (about three times the cost in Lua 5.1). Scopes, handles, connections and SyncSets keep `rawget` and `rawset`: they have metatables whose `__index` is a prototype, and a missing field must not resolve to a method. The same paths ask one probe about every value (`onAddonMessage`, `readSendRequest`, `classifySendResult`) instead of letting `isSecret` read it again for each. The probe, `securecallfunction` and the client's `Success` result are resolved once at load into `HOST` (revision 10); a function absent then is read with `readHostFunction` on each call, so one installed later is honoured. `driveChunks` reads the probe and both send functions once per run and passes them to `transmit`, computes the mode and rate once per run, skips `peekNextPipe` while exactly one message is queued and its pipe is still at the ring index served last (only the rotation slot is found again), and calls `assignStreamId` for a message's first chunk only. `driveChunks` ends a run on an empty queue before walking the priority rotation, and `peekNextPipe` skips a priority with nothing queued; `dequeueRecord` and `closeStream` take the head of their list without searching.

## The local-variable budget

Lua 5.1 allows 200 local variables in one function, and the file's main chunk is one function. Constants are therefore grouped into tables (`WIRE`, `REASON`, `POLICY`, ...) and public methods are defined on method tables (`ScopeMethods`, ...) that `commitMethods` copies onto the prototypes. Helpers used by one function only live in `do` blocks with the function forward-declared (`assignStreamId`, `noteDrop`, `armDriverRun`, ...). The main chunk is at the limit: at its peak 200 locals are live (the most whose ranges overlap in `luac -l -l`, `LOGOUT` and `LogoutClose` included; revision 5 measured this after one more file-scope local failed to load). Revision 5 adds no local: its new state is reached through `state` (`state.spares`) and its new constants live in the existing `WIRE` and `POOL_RETAINED` tables. Revision 6 folds seven file-scope locals into `do` blocks (the three refusal texts of `LIMIT_RANGES`, `hasMethods` behind `validatePublicSurface`, `newQueue` inside `newState`, and the namespace lookups that find Registry) and adds six (`deferred`, `flushDeferred`, `deferCallback`, `runInline`, `acquireRecord`, `releaseRecord`), leaving the peak at 199. Revision 7 adds no local: the lookup time lives in `state` and its period in `POLICY`. Revision 8 adds one, `SendPath`, and folds two into it (`refuseSend` and `targetFits` became `SendPath.refuse` and `SendPath.targetFits`; the raw send path is `SendPath.readRawRequest` and `SendPath.enqueueRaw`), leaving the peak at 198. Revision 10 adds one, `HOST`, for the host values resolved at load, leaving the peak at 199; the lazily made key suffixes live in `WIRE`. Revision 11 moves the SyncSet machinery out (`hashValue`, `encodeSyncMessage`, `receiveSync`, `SYNC`, `FNV`, `SyncSetMethods` and the scope method's two readers), drops `SchedulerKit` and `SchedulerScope`, and adds `armDriverRun` and `Parts` (the part interface constant, member lists, stub installer and message), leaving the peak at 188. A change that needs a file-scope local must first fold existing ones into a table.
