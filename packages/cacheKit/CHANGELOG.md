# Changelog

## 0.3.0 — 2026-11-18

- Changed: `SetLimits` and `GetLimits` called with a dot (on anything but the facade) raise `CacheKit:SetLimits must be called on the CacheKit facade; use CacheKit:SetLimits(...)`, likewise for `GetLimits`. The `; use ...` hint is new, which is why this is a minor version. A secret receiver is now never compared with the facade: its type is tested first.
- `isSecret` (formerly `isSecretValue`), `validateFacade` and `describeKey` are now the shared helper blocks (`tooling/shared/lua/`, kept in step by `python3 -m tooling.shared.sync`). The argument checks follow the probe rule: `issecretvalue` is read once at load and, on a host that had none at load, again at each check, so a probe installed after load is now honoured; a probe present at load is kept. The snapshot `fill` keeps the probe bound at load, so its hot path pays no extra call. `describeKey` names a secret key `<secret>`, a branch no caller reaches (a key read by `next` cannot be secret, and `fill` refuses a secret key first). The `SetLimits` validation stays CacheKit's own.
- `docs/API.md`: *Secret values* now comes before *Limits*, the order every package's API.md uses; *Loading* lists `issecretvalue`; *Error behaviour* gives the facade message.
- Implementation revision 8. No state or object layout changed: an embedded revision 7 is upgraded in place, caches and limits kept.
- New specs: `SharedHelpers_spec.lua` (the facade message with the hint and a probe installed after load, both failing on revision 7; the probe kept from load; the upgrade over the committed revision 7 file in `tests/fixtures/CacheKit-revision7.lua`) and `Conformance_spec.lua` (the repository's conformance suite; its limits and arguments groups are pending, see the spec). `ErrorLevels_spec.lua` expects the new facade message. 181 → 191 specs.

## 0.2.9 — 2026-11-15

- Fixed: three refusals passed a caller's table key to `tostring` to name it: `SetLimits` with an unrecognised limit name, a constructor option table with an unknown field (`NewLru`, `NewTtl`, `Memoize`, `NewSnapshot`, `Lazy`), and a snapshot `fill` given the same key twice in one refresh. `tostring` on a table or userdata runs its `__tostring`, foreign code that could raise (or answer a secret on Retail) inside CacheKit, so the caller saw that error instead of the real refusal. A string key is still shown as written and a number or boolean through `tostring`, which runs no foreign code, so `limits.1` and `unknown field "aaa"` are unchanged; any other key is named by its type: `CacheKit:SetLimits limits.<table> is not a recognised limit`, `CacheKit:NewLru options contains unknown field "<table>"`, `CacheKit.Snapshot fill received key "<table>" twice in one refresh`. Documented in `docs/API.md`.
- Implementation revision 7. No state or object layout changed: an upgrade over revision 6 replaces the methods and keeps every cache, snapshot, lazy tree and queue; snapshot `fill` closures an older copy created use the new message at once through the shared dispatch table.
- Specs: a table key whose `__tostring` raises is named by its type at the caller's line on all three paths and its `__tostring` never runs, and an in-place upgrade from revision 6. 179 → 181 specs.

## 0.2.5 — 2026-09-24

- A `Memoize` `cacheable` predicate that answers with a secret value (Retail 12.x) no longer raises inside CacheKit. Testing a secret for truth raises (`attempt to perform boolean test on ... a secret boolean value`, measured on Retail 12.1.0 b69933), so the answer is asked about with `issecretvalue` first and a secret answer counts as `false`: the result is returned to the caller without being remembered. `docs/API.md` documents it under `cacheable` and *Secret values*.
- Implementation revision 5. No state or object layout changed: an upgrade over revision 4 replaces the methods and keeps every cache, snapshot, lazy tree and queue, and memoised functions an older copy created run the new check at once.
- Audit of the other truth tests on values CacheKit did not create: the memoised function's result and the lazy tree resolver's result are only asked `type(value) == "nil"`; pcall results and the Registry and EventKit lookups are Kit-created or type-checked; no option is a boolean flag. Nothing else changed.
- Specs: a secret `cacheable` answer leaves the result unremembered, and an in-place upgrade from revision 4; the older upgrade specs compare with the working revision instead of a fixed number.

## 0.2.4 — 2026-09-24

- Secret values: API.md *Secret values* states that a secret used as a key raises the client's own error, `attempted to index a table that cannot be indexed with secret keys`, and that the negative-entry check compares a stored value by identity with CacheKit's own marker table, which the client allows for a secret number or string because the two differ in type; INTERNALS.md (*Negative entries*, snapshot `fill`), the README and the source comments on the probe and the negative-entry check follow no longer claim that comparing a secret with anything, `nil` included, raises, or that a raw identity test is safe whatever the other side. They state what was measured on Retail 12.1.0 b69933 (2026-09-24): a secret compared with a value of its own type raises (`==`, `~=`, `<`, `<=` and `rawequal` alike) and a secret used as a table key raises, while a comparison with `nil` or with a value of another type answers without raising. The `type(value) == "nil"` rule stays, as the repository's uniform rule that never compares anything. Comments and documentation only: `luac -s -l` gives the same instruction listing before and after, so the implementation revision is unchanged.

## 0.2.2 — 2026-09-24

- Implementation revision 4 applies the repository nil rule: the absence of a caller's key, value, option table, option field or limit, and of what a memoised function or a lazy tree's resolver returned, is tested with `type(value) == "nil"`, never by comparing the value with `nil`. The Registry lookup, the results of `Registry:Bootstrap` and the EventKit that `Registry:Find` returns are tested the same way.
- `maxEntries` (`NewLru`, `NewTtl`, `Memoize`, `NewSnapshot`, `Lazy`), `NewQueue`'s `capacity` and `SetLimits` values are asked about with `issecretvalue` before they are compared with `CacheKit.UNBOUNDED` or a number; a secret is refused at the caller's line with the message any other invalid value gets.
- A stored value is compared with the negative-entry marker by raw identity, which never compares a secret, in `Get`, `Peek` and memoised calls, so a secret value a caller stored (or a memoised function returned) is handed back without being compared. Keys still must not be secret, as before.

## 0.2.1 — 2026-09-24

- Fixed: a lazy tree expanding a node that existed only as structure could lose it. When the tree was full and the node's only expanded descendant was the least recently read node, eviction dropped that descendant and the pruning after it detached the node being expanded, which was then kept as expanded and linked in the recency list but no longer reachable from the root: the value was unreachable, the node sat on the free list while linked, and a later eviction raised inside CacheKit (`attempt to index local 'parent'`). `expandNode` now expands the node first and evicts afterwards, so pruning stops at it; the eviction order is unchanged.
- Implementation revision 3. The state schema and every object layout are unchanged, so an upgrade over revision 2 replaces the methods and keeps the state, the limits and every cache, snapshot, lazy tree and queue; lazy trees revision 2 built run the corrected expansion at once.
- The randomized specs (the lazy tree workload and the LRU, negative-entry and queue model comparisons) drew from the low bits of a power-of-two-modulus generator, whose short periods kept the workload from ever reaching the case above; they now draw from the high bits. The lazy tree workload also runs with two expanded nodes, where almost every miss evicts, and checks that every node in the recency list is attached under the root. The upgrade specs load the next revision relative to the current one instead of a fixed number, and a spec covers the upgrade from revision 2.
- API.md: the paragraphs on unbounded caches and the shared sentinel moved from under `GetLimits` to the *Limits* section they describe. README: a failed snapshot read also restores the values it changed.
- 171 specs.
- `CacheKit` API generation 1 is unchanged.

## 0.2.0 — 2026-09-24

- Added `cache:PutNegative(key, ttlSeconds)` on caches with an age limit (`NewTtl`, or `Memoize` with `ttlSeconds`): a negative entry records that a key has no value, for `ttlSeconds` of its own, independent of the cache's `ttlSeconds`. `Get` and `Peek` answer a live negative entry with `nil, "negative"` and `Get` counts a hit; a memoised function answers `nil` without calling `fn`. The entry takes an ordinary slot, is evicted by recency, and `Set`, `Delete` and `Clear` remove it. A plain LRU cache refuses it at the caller's line (`requires a cache with an age limit`), because nothing there would ever expire it. The marker is one table kept in the package state, so no entry field was added and revision 1 entries keep their layout.
- Added the `Memoize` option `cacheable`, a predicate called with `fn`'s first result and the key once the result is known to be non-`nil`. A result it returns `false` or `nil` for is returned to the caller without being remembered, so an incomplete answer (item data the client has not loaded yet) is computed again next time. `cacheable` must be a function; an error it raises propagates and remembers nothing.
- Added `CacheKit:Lazy(resolve, options)`: a namespace tree expanded on demand. `tree:Get(parts...)` calls `resolve(parts...)` once per path of string or number parts and keeps the first result unless it is `nil`; `tree:Peek` reads without resolving; `tree:Invalidate(parts...)` removes the node with every descendant and forgets the value of every ancestor on the path (a value derived from a subtree is stale once part of it changed), leaving siblings untouched, and returns how many expanded nodes it forgot; `Clear`, `GetCount`, `GetStats`, `Close` and `IsClosed` complete the handle. Bounded by `maxEntries` expanded nodes (128 by default, or `CacheKit.UNBOUNDED`), evicting the least recently read one; a node whose value is evicted or invalidated stays as structure while a descendant is expanded, and every node without a value has an expanded descendant, so structure never outgrows the bound times the path depth. A hit allocates nothing; blank nodes are recycled through a free list bounded like a cache's.
- Added `CacheKit:NewQueue(capacity, overflow)`: a ring of `capacity` slots allocated at construction with the overflow policy required up front: `"dropOldest"` (stores, returns `true, oldest`), `"dropNewest"` (returns `false, value`) or `"reject"` (returns `false`). `Push`, `Pop`, `Peek`, `Iterate` (oldest to newest, `position, value`, no allocation), `Clear`, `GetCount` and `GetCapacity` are O(1) per step and allocate nothing after construction. `capacity` must be an integer from 1 to the package-wide `maxQueueCapacity`, refused at the caller's line above it with `capacity must be an integer from 1 to 1024 (CacheKit:SetLimits maxQueueCapacity)`; `CacheKit.UNBOUNDED` is refused with its reason, because the ring is allocated when the queue is created. A `nil` value is refused at the caller's line.
- Added `CacheKit:SetLimits(limits)` and `CacheKit:GetLimits()`, CacheKit's first package-wide limit: `maxQueueCapacity` (default 1024, ceiling 65536) bounds the capacity one `NewQueue` call may allocate, following the framework decision that a preallocated ring is bounded through a limit rather than `UNBOUNDED`. `SetLimits` validates the whole table first and raises at the caller on an unknown name, a value outside 1 to 65536, `UNBOUNDED` or a non-table; lowering it never shrinks an existing queue. `GetLimits` returns a fresh table. Both require the facade as receiver. The limits are shared by every embedded copy and kept across an in-place upgrade.
- Implementation revision 2, with package state schema 2: the state gains `lazyMetatable`, `queueMetatable`, the `negative` marker and the `limits` table, and the facade gains the `LazyTree` and `Queue` prototypes. An upgrade over revision 1 adds them (with the default limits) and keeps every cache, entry, memoised function, subscription and snapshot; memoised closures revision 1 created keep calling `dispatch.memoizedCall` with three arguments, which is why the new `cacheable` parameter is the last one. The public-surface predicate now requires `Lazy`, `NewQueue`, `SetLimits`, `GetLimits`, `PutNegative` and both prototypes; the state predicate requires the four new state fields and every limit within its ceiling.
- The `Limits` section of API.md names the lazy tree bound, the queue capacity and `maxQueueCapacity`. `GetStats` is shared by caches and lazy trees.
- 168 specs: negative entries (own expiry, hit counting, `Peek`, replacement, eviction, memoised `nil`, refusal on an LRU cache, clock-less host, and a 5,000-step comparison against a naive TTL model mixing `Set`, `PutNegative` with 1 to 3 second limits, `Get`, `Delete`, `Clear` and clock advances), `cacheable` (pass-through, arguments, `nil` answers, errors, closing the cache), lazy trees (once-per-path resolution, ancestor and descendant invalidation, unexpanded paths, eviction order, structure kept for descendants, `UNBOUNDED`, the free-list bound, re-entrant resolvers, a resolver that closes the tree, and a 3,000-step randomized workload with resolvers that invalidate their own path or clear the tree mid-resolve, walking the tree after every step to check that every node without a value has an expanded descendant, that `parent` and `childCount` agree with the `children` tables, and that the recency list holds exactly the expanded nodes), queues (every policy, wrap-around, iteration, `Clear`, capacity one, and a 1,000-step model comparison per policy), `maxQueueCapacity` (default, ceiling, lowering without shrinking, `UNBOUNDED` and invalid values, atomic `SetLimits`, fresh `GetLimits`, shared across embedded copies and an upgrade), allocation guards for negative hits, results the predicate lets through, lazy hits, re-expansion and queue traffic, error levels for every new failure, and the in-place upgrade from revision 1 state.
- `CacheKit` API generation 1 is unchanged.

## 0.1.0 — 2026-09-23

- Added CacheKit API generation 1, implementation revision 1.
- Added `CacheKit:NewLru({ maxEntries })` and `CacheKit:NewTtl({ maxEntries, ttlSeconds })`: bounded least-recently-used caches, the second with an age limit, with `Get`, `Set`, `Peek`, `Delete`, `Clear`, `GetCount`, `GetStats`, `ClearOn`, `Close` and `IsClosed`. `maxEntries` is required. The recency order is an intrusive doubly linked list over the key hash, so `Get` and `Set` are O(1); entry tables freed by `Delete`, expiry and `Clear` go to a free list bounded by `maxEntries`, and eviction reuses the evicted entry directly.
- Age limits read `GetTimePreciseSec`, which is optional: without it every age limit is disabled.
- Added `CacheKit:Memoize(fn, options)` for one string or number key, bounded by 128 entries by default, with an optional `ttlSeconds`. It returns the memoised function and the cache behind it.
- Added `CacheKit:NewSnapshot(read, options)` with `Refresh`, `Get`, `GetCount`, `Pairs`, `Close` and `IsClosed`. `Refresh` reports added, removed and changed keys in three reused arrays, and allocates nothing for a key whose value did not change. A snapshot accepts at most `maxEntries` keys per refresh, 1024 by default.
- Added `cache:ClearOn(eventName)` through EventKit API 1, an optional dependency found with `Registry:Find` when it is called. `Close` releases the subscriptions.
- Memoised functions, snapshot fill functions and clear-on-event callbacks call through a shared dispatch table, and caches and snapshots keep their metatables across upgrades, so an in-place upgrade keeps every entry and replaces the behaviour behind every closure.
- A snapshot whose `read` raises rolls back the keys that read added and removes nothing, so it never holds more than `maxEntries` keys however many reads fail in a row, including repeated `maxEntries` refusals. `Refresh` re-raises the reader's error value unchanged with level 0, so the traceback ends at `Refresh`.
- A failed refresh also puts back the previous value of every key it changed, through an array kept beside the `changed` array, so the snapshot is exactly its last successful refresh and the next successful refresh reports the change instead of losing it. The rollback also clears the result-array slots the failed refresh wrote, so the next refresh's `added` and `changed` arrays hold only its own keys.
- `cache:ClearOn` raises a refused host registration at its caller's line as `CacheKit.Cache:ClearOn could not connect <event>: <reason>`, and the event can be connected again later.
- A snapshot's `fill` refuses a secret key or value (Retail 12.x, through `issecretvalue`) at the reader's line before any comparison. API.md documents the secret-value rule for caches and snapshots, and the roster example covers party units as well as raid units.
- `CacheKit.UNBOUNDED`, one sentinel table kept in the package state so every revision shares it: every `maxEntries` option (`NewLru`, `NewTtl`, `Memoize`, `NewSnapshot`) accepts it to lift the bound on the consumer's own data. The free list of an unbounded cache keeps at most 1024 blank entries. API.md gains a *Limits* section naming every limit, its default and how to open it.
- 96 specs, including allocation guards, a 5,000-step property test against a naive LRU model that also checks the free-list bound, an in-place upgrade spec, limit specs for `UNBOUNDED` and the sentinel carried across an upgrade, and regression specs for repeated failing reads, a change made during a failed refresh, a refused `ClearOn` registration and secret values.
