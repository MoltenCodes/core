# ApiKit

ApiKit is the flavour-aware, typed, documented wrapper over the public World of
Warcraft addon API. Its surface is generated from the client's own API
documentation tables: one file per client flavour binds every documented
Blizzard function to a readable name by direct alias, and the matching LuaCATS
definitions let an editor complete exactly what that flavour has.

```lua
local api = wow.retail.api          -- or MoltenCodes.wow.retail.api, always there

local elapsed = api.profiler.measureCall(myFunction)   -- C_AddOnProfiler.MeasureCall
api.timer.after(1, callback)                            -- C_Timer.After
local name = api.unit.name("player")                    -- UnitName
api.events.playerLogin                                  -- "PLAYER_LOGIN"
api.enums.phaseReason.Sharding                          -- Enum.PhaseReason.Sharding
```

Every entry is the Blizzard function itself, reached through one more table
index; nothing is wrapped, translated or hidden, and the raw API stays valid
beside it. A function the running build does not have is simply absent from
the wrapper. The design is [`docs/API_KIT_DESIGN.md`](../../docs/API_KIT_DESIGN.md);
the naming rules are [`docs/NAMING.md`](docs/NAMING.md); the facade's contract
is [`docs/API.md`](docs/API.md).

## Flavours

| Flavour | Namespace | Runtime file |
|---|---|---|
| Retail | `wow.retail.api` | `flavours/Retail.lua` |
| Classic Era | `wow.classic.era.api` | `flavours/ClassicEra.lua` |
| Mists of Pandaria Classic | `wow.classic.mop.api` | `flavours/ClassicMop.lua` |
| Public Test Realm | `wow.ptr.api` | `flavours/Ptr.lua` |
| Beta | `wow.beta.api` | `flavours/Beta.lua` |

A client runs one flavour. ApiKit detects it once, at load, from
`WOW_PROJECT_ID`, `IsTestBuild()` and `IsBetaBuild()`, fills that flavour's
namespace from its runtime file and leaves the other four as empty tables, so
`wow.classic.era.api` on a Retail client is an empty table rather than an
error. `ApiKit:GetFlavor()` says which one is live. A Burning Crusade Classic
client is `"unsupported"` and gets no surface.

The runtime files are generated by `python3 -m tooling.api.generate` from the
metadata under `metadata/<flavour>/` and are never edited by hand. The
metadata's own description is [`tooling/api/SCHEMA.md`](../../tooling/api/SCHEMA.md).
All five flavours are committed. The counts are documented functions, of
which the bound ones are wrapper entries and the rest are methods of script
object types described in the types only: Retail (client 12.1.0, build 69933:
6,338 functions, 4,900 bound in 312 namespaces; 1,782 events, 844
enumerations), Classic Era (1.15.9, build 69722: 4,589 functions, 3,229 bound
in 261 namespaces), Mists of Pandaria Classic (5.5.4, build 69934: 4,590
functions, 3,230 bound in 261), the Public Test Realm (12.1.5, build 69952:
6,437 functions, 4,967 bound in 316) and Beta (12.0.1, build 66220, the
mirror's last beta export: 5,942 functions, 4,652 bound in 304). `metadata/<flavour>/provenance.json` names the build each capture
was taken from; `metadata/<flavour>/history.json` is its build history. A
capture is only as current as the mirror branch it came from: the Beta branch
last moved in March 2026, so its bindings describe that build until the
branch moves again. The Markdown reference of each flavour is attached to every release
(`MoltenCodes-ApiKit-reference.zip`) and is built locally with
`python3 -m tooling.api.generate --all --reference-out build/reference`; it
is not committed.

## The `wow` global

The framework's rule is one global, `MoltenCodes`; the namespaces above are
always reachable as `MoltenCodes.wow.<...>.api`. ApiKit also publishes the
short `wow` global, because `local api = wow.retail.api` is the intended
usage, under one rule: **only when nothing else owns the name.** An existing
`wow` that is not ApiKit's is left alone and `ApiKit:GetGlobalStatus()`
returns `"taken"`; fall back to `MoltenCodes.wow` then.

## Editor support

Point your `.luarc.json` at the flavour you write for. The definitions live in
this repository under `packages/apiKit/types/<flavour>/`; they are development
files, never shipped in a bundle or loaded by the client, so copy the flavour's
directory next to your project (or reference a checkout) and list it:

```json
{ "workspace": { "library": ["vendor/apiKit-types/retail"] } }
```

List one flavour at a time: every flavour's `api.lua` declares the `wow` and
`MoltenCodes` globals, so two flavours in one workspace make the language
server report duplicate classes. An addon that supports several flavours
switches the library entry when it works on another flavour's code.

## Embedding

[`../../docs/EMBEDDING.md`](../../docs/EMBEDDING.md) is the addon author's guide:
directory layout, supported Interface numbers, taint, `/reload` semantics and
troubleshooting. This package's load order inside a consuming addon is the
facade, then the runtime file of every flavour the addon supports:

```toc
Libs\MoltenCodes\registry\Registry.lua
Libs\MoltenCodes\apiKit\ApiKit.lua
Libs\MoltenCodes\apiKit\flavours\Retail.lua
Libs\MoltenCodes\apiKit\flavours\ClassicEra.lua
```

Minimum footprint: Embed 3 files: Registry, ApiKit, one flavour file.

Direct runtime dependencies: Registry API 2. A flavour file for a client the
addon is not running on costs its parse and one registration call, nothing
else; the flavour files depend only on the facade, never on each other. Two
addons that embed the same flavour install it once: the first file to load
fills the namespace and later copies are dropped.
