# Changelog

## 0.7.0 — 2026-11-18

A smaller core: spec profiles and plain defaults become parts, plans are sparse, and the hand-written helpers take their shared blocks (roadmap package P, "settingsKit SpecProfiles part", "settingsKit Defaults part" and "settingsKit core trims", core decision 20). API generation 1.

- Changed: spec profiles moved to the new part `parts/SettingsKit-SpecProfiles.lua` (part revision 1; EventKit optional): `SettingsKit:GetSpecIndex`, `db:SetSpecProfile`, `db:GetSpecProfile`, `db:ApplySpecProfile` and the switch on spec events. Without the part the four members stay on the facade and the database prototype and raise at the caller's line: `SettingsKit:GetSpecIndex is in SettingsKit's SpecProfiles part, which is not loaded: add settingsKit\parts\SettingsKit-SpecProfiles.lua` (and `SettingsKit.Database:SetSpecProfile`, `GetSpecProfile`, `ApplySpecProfile`). The core keeps the `specProfiles` section: it is created and checked as before, `ResetDatabase` empties it and `DeleteProfile` forgets the assignments naming the deleted profile, with or without the part. `Open` applies a character's assignment only while the part is loaded. With an EventKit from revision 23 (unit events in its Units part), the part connects its listener only when `EventKit:HasPart("Units")`; an older EventKit is asked for `ConnectUnit`. The manifest says so: the part's optional `eventKit` dependency names `"parts": ["Units"]`.
- Added: `SettingsKit:HasPart(name)`, whether a part is loaded, without raising for an unknown name; it refuses a dot call, a secret name and a non-string at the caller's line.
- Added: the part `parts/SettingsKit-Defaults.lua` (part revision 1): `SettingsKit:Open` and `db:RegisterNamespace` accept a scope given as plain AceDB-style defaults. The write rules are inferred from each default exactly as AddonKit's `MC:Database` infers a SchemaKit schema and checked without SchemaKit, with SchemaKit's failure shape and wording; a SchemaKit node inside the defaults is kept as a leaf. Without the part a plain scope raises `SettingsKit:Open plain defaults are in SettingsKit's Defaults part, which is not loaded: add settingsKit\parts\SettingsKit-Defaults.lua` (until now: `... must be a SchemaKit schema node or sealed schema`). Defaults that have no SettingsKit form are refused at the caller's line, with AddonKit's reasons.
- Changed: SchemaKit is an optional dependency. The core loads without it and finds it through `Registry:Find` when a scope is a SchemaKit schema; without it the depth bound is 16, SchemaKit's default. A database-only addon with plain defaults embeds Registry, SignalKit, SettingsKit and the Defaults part.
- Changed: plans hold only the fields they use and fast checks only the bounds a field declares (plan layout 3); revision 15's layout 2 plans are read alike. The sealed depth probes for a SchemaKit older than revision 6 are gone: with such a SchemaKit a nested write takes the full check.
- Changed: the secret probe, error reporting, key descriptions, the facade check and the limits loop are the shared helper blocks (`tooling/shared/lua/`). Visible: `SetLimits` names the accepted limits in its unknown-name refusal (`... is not a recognised limit; it accepts maxProfileNameLength, pathKeyLimit`) and names a secret key `limits.<secret>` in it instead of `SettingsKit:SetLimits limits must not have a secret key`; a host error handler that raises while a logout compaction failure is reported now falls back to `print` instead of propagating; a probe present at load is kept (one absent at load is read per call). `Open`'s `savedVariable` and profile names are asked about secrecy before their type, so a secret is named as secret whatever its type.
- Not taken: one rule table for the option readers (record "core trims", point 2c): with the four readers stubbed out entirely the core measured only 3.1 KB smaller, so a rule table and its reader could not save the 2 KB the record requires.
- Resident memory, host Lua 5.1.5, debug information kept, 2026-11-18, SchemaKit loaded: core 192.1 KB → 185.1 KB; Defaults part 20.9 KB; SpecProfiles part 15.3 KB. Registry, SignalKit, SettingsKit and the Defaults part, without SchemaKit: 320.8 KB (the set with SchemaKit: 388.4 KB). The bench-shaped schema plus its first `Open`: 49.9 KB → 40.1 KB; as plain defaults 27.0 KB.
- Implementation revision 16. An in-place upgrade from revision 15 keeps every database, view and plan; with the SpecProfiles part absent it keeps revision 15's spec-profile members and entries until the part loads (`tests/fixtures/SettingsKit-revision15.lua` is a byte copy of revision 15 for these specs). A revision 15 copy loaded after revision 16 yields, and its spec calls raise the not-loaded message until some addon embeds the part.
- Specs: 370 → 420. `SpecProfilesPart_spec.lua`, `DefaultsPart_spec.lua`, `CoreTrims_spec.lua`, `Conformance_spec.lua`, and the existing specs adjusted to the parts and messages. The Defaults part's allocation guard carries the `#allocation` tag like every other allocation spec, so the coverage run, whose line hook allocates, leaves it out.

## 0.6.0 — 2026-11-15

AceDB-3.0's namespaces, its four other scopes and its other database callbacks (roadmap package O, "settingsKit AceDB scopes, profile lifecycle signals, `missingOk`, and the core side of namespaces" and "settingsKit Namespaces part"). API generation 1, additive.

- Added: scopes `race`, `factionrealm`, `factionrealmregion` and `locale`, in sections of the same names and keyed as AceDB-3.0 keys them (`UnitRace("player")`'s file name; `"<faction> - <realm>"`; that plus `" - <region>"`, the region from `GetCurrentRegion()`, else `GetCurrentRegionName()`, else `"TR"`; `GetLocale()` in lower case), so data BridgeKit imports from AceDB keeps its keys. Their keys are read, and their sections created and checked, only for a schema that declares them. Views, `OnChange`, `Getter`, `Validate`, `Pairs` and compaction treat them as they treat `realm` and `class`.
- Added: `db:OnNewProfile`, `db:OnProfileShutdown` (before a switch, with the profile being left), `db:OnDatabaseShutdown` (at logout with EventKit, before compaction, also for a read-only database) and `db:OnDatabaseReset` (first in `ResetDatabase`), through the existing signals created by their first listener; and `db:IsNewProfile()`, whether this session created the current profile's table, for the first profile `Open` creates before any listener can connect.
- Added: `{ missingOk = true }` for `db:CopyProfile(from, options)` and `db:DeleteProfile(name, options)`, which then return `false` for a missing profile (AceDB-3.0's `silent`). Changed: both now return `true` when they did their work.
- Added: the part `parts/SettingsKit-Namespaces.lua` (part revision 1): `db:RegisterNamespace(name, schema)` and `db:GetNamespace(name, { missingOk })`. A namespace is a database over `MyAddonDB.namespaces[name]`, in AceDB-3.0's namespace layout, with views, validated writes and signals of its own, following its parent's profile. The parent's `SetProfile` (spec switches included), `CopyProfile`, `ResetProfile`, `DeleteProfile` and `ResetDatabase` change every namespace, refusals first, then every change, then the namespaces' signals and the parent's; namespaces saved but not registered this session get AceDB's raw copy, reset and delete; the parent's `Compact` and the logout compaction include the namespaces, and logout removes empty namespaces. The `namespaces` section, reserved until now, holds them. Without the part, reading `db.RegisterNamespace` raises a message naming the file to add.
- Added: the `Open` option `maxNamespaces` (256 by default, `SettingsKit.UNBOUNDED` accepted), kept on the database only when passed.
- Changed: the profile methods `SetProfile`, `CopyProfile`, `DeleteProfile`, `ResetDatabase`, `SetSpecProfile` and `ApplySpecProfile` refuse a namespace, naming its parent; `GetProfiles` and `GetSpecProfile` on a namespace answer its parent's.
- Internal: the four scope tables are one `Scopes` table (main-chunk locals 195 to 193); the added scopes come last and the schema walks stop once they have seen every declared scope; the helpers of the new methods live in `DatabaseHelpers`; `state.parts`, `state.helpers` and `state.createdProfiles` are new. Implementation revision 15. An in-place upgrade from revision 14 adds the three tables and keeps every database, view, listener and getter.
- Measured on host Lua 5.1 (2026-11-15), each ratio against AceDB-3.0 in its own run, revision 14 then 15 (`python3 -m tooling.bench.run --workload settings` with two added cases): reads, getters and writes unchanged within noise (read-saved 2.93x and 2.87x, read-nested 2.12x and 2.09x, write-scalar 343 ns both); switch-profile 0.20x to 0.21x; open-empty 2.90x to 3.31x and open-populated 2.31x to 2.41x (counted, an `Open` runs 8% more VM instructions: 1,178 to 1,272, the longer scope tables and the checks of the added scopes; the rest of the gap is run-to-run noise on a loaded host), bytes unchanged (3,691 B and 4,704 B). New: switch-profile with 10 namespaces 0.25x (4.6 µs, 0 B, against 18.6 µs and 1.9 KB), register-namespace 2.86x (7.8 µs against 2.7 µs), 4,038 B held with its profile view built against AceDB-3.0's 3,280 B (1.23x). Compiled chunk held on host Lua: core 186.9 KB to 211.2 KB; the part 33.9 KB, held only by addons that load it.
- Specs: 298 → 370. `AceScopes_spec.lua` (the four scopes, keys, fallbacks, unavailability, no host call when undeclared, sections and migrations), `LifecycleSignals_spec.lua` (the four signals, their order, logout, `IsNewProfile`, `missingOk`, `maxNamespaces`), `Namespaces_spec.lua` (registration, the layout, read-only parents, every cascaded operation and its signal order, unregistered namespaces, logout cleanup, the part loaded late, not loaded, twice and without its core, an in-place core upgrade, no allocation on reads, writes and switches), the revision 15 error levels, and the upgrade from revision 14 (`Bootstrap_spec.lua`). Adjusted: the revision 13 upgrade spec accepts any later revision.

## 0.5.0 — 2026-11-15

Reads at AceDB's cost, lazy views and cheaper writes (roadmap package O, "settingsKit read-through views", core decisions 18 and 19). API generation 1, additive.

- Changed: views read through chained tables. Each view has a metatable of its own whose `__index` is a table (the child views, the saved table, the scalar defaults), so the VM answers `db.profile.scale` without a SettingsKit call. Writes still reach `__newindex` and are validated at the writer's line with the same messages. Every mutation that changes saved tables rebinds the chains it changed afterwards (a write the written view's path and subtree, the database methods every built view, `Compact` also when it raises halfway). A view whose plain-table default is not stored yet, or whose saved table carries a foreign metatable, reads through a SettingsKit function as before.
- Changed, documented under *The saved table*: while a database is open its saved tables carry a SettingsKit metatable (marked `__settingsKitSaved`) and read their scalar defaults, so `MyAddonDB.profiles.Default.scale` read directly answers the default, as AceDB-3.0's tables do. `rawget`, `next` and `pairs` see only what is saved, a plain-table default is never answered that way, nothing changes on disk, and `scanValue` accepts such a table as plain.
- Changed (core decision 19b): the read-side secret-key probes are removed from views and from the database's `__index`. The client refuses a secret key before any `__index` runs (Retail 12.1.0 b69933, `docs/EMBEDDING.md`), so they could never fire there; a read with a secret key raises the client's `attempted to index a table that cannot be indexed with secret keys` at the same line. The messages `... cannot be read with a secret key` and `SettingsKit databases cannot be read with a secret key` are gone. Every other secret check stays. The client suite asserts the client's refusal.
- Changed: views are built on first use. `Open` gives each scope a proxy with nothing behind it, a record view gives its fields proxies built on their own first use, and a view's probe table is built by its first full check; `db.<scope>` stays a raw field of the database. Layout sections are still created by `Open`, as *The saved table* promises.
- Changed: the `char` key takes the name from `UnitNameUnmodified("player")`, which no name-changing effect alters, as AceDB-3.0 does, and from `UnitName("player")` when the client has none or its answer is not usable. Outside such effects both answer alike, so saved data keeps its key.
- Added: `SettingsKit:GetCharacterKey()`, the character key `Open` uses now, or `nil`, for an importer (BridgeKit's AceDB import) that must key data the way SettingsKit reads it.
- Changed: a write of a value that is not a table to a scalar field of a verified record view takes one fused path, and the depth limit is read through `SchemaKit:GetLimit` without allocating (the depth probes remain for a SchemaKit without it). Messages and error levels are unchanged.
- Changed: `db:Getter` returns a closure reading through the view (`proxy[key]`, or `db[scope][key]`), one Lua call plus a view read; getters made by revisions 7 to 13 keep working. `docs/API.md` now says a plain read is the hot-loop answer.
- Changed: a database creates its `_signals` table with its first profile listener and an empty saved variable skips the layout check, so a database with two scopes keeps to 16 fields.
- Measured on host Lua 5.1, each ratio against AceDB-3.0 in its own run (`python3 -m tooling.bench.run --workload settings`, revision 13 then 14): read-saved 31.7x to 2.8x, read-default 29.3x to 3.7x, read-nested 34.4x to 1.9x, read-entry-default 40.2x to 1.9x, read-getter 2.5x to 1.65x, read-getter-entry 1.6x to 1.15x, write-scalar 53x to 35x, write-nested 190x to 102x, open-empty 4.7x and 8.3 KB to 3.1x and 3.7 KB (AceDB 3.3 KB), open-populated 2.6x and 7.7 KB to 2.3x and 4.7 KB, switch-profile 0.24x to 0.19x. An open database with one profile read holds 3.0 KB beyond its saved variable (revision 13: 3.9 KB, AceDB-3.0: 3.4 KB).
- Implementation revision 14, node layout 4. An in-place upgrade from revision 13 gives every live view its own metatable and chain (the shared view metatable's protection is lifted for the swap and restored), moves every entry cache to the shared entry-cache metatable, and keeps every database, view, listener and getter; a database an older revision opened builds each new profile view at once, since a getter that revision made expects one.
- Specs: 273 → 298. `ReadThrough_spec.lua` (25) covers the chains, rebinding, views built on first use, the fused write, the depth limit, the character key and the upgrade from revision 13. Adjusted: raw saved-table inspections use `rawget` (`Writes_spec.lua`), a saved table carries only SettingsKit's metatable (`Aliasing_spec.lua`), the secret-key read specs assert that no probe is asked (`Aliasing_spec.lua`, `Writes_spec.lua`, `Defaults_spec.lua`, `Bootstrap_spec.lua`), allocation specs read a view once before measuring, upgrade specs build views before laying an older layout over them and expect node layout 4.

## 0.4.1 — 2026-11-15

Fixes from a review of spec profiles. API generation 1 and the saved-table layout are unchanged.

- Fixed: an assignment could stop applying. A database remembers the spec index it last applied, and a spec event skips a database that already applied the event's index; but a database whose character had no assignment any more (all cleared, or removed by `DeleteProfile` or `ResetDatabase`) was skipped by every event and kept the old index. After the character changed specialization and came back, an assignment made meanwhile for that index matched the stale index and was never applied. Every spec event now records the index for a database without an assignment too.
- Fixed: an in-place upgrade undid a manual profile choice. Loading a newer copy applied the current index's assignment again to every open database, also to those a revision with spec profiles had opened and kept following the events, so a newer copy loading in the middle of the session (a load-on-demand addon) switched a player who had chosen another profile by hand back to the assigned one. Only databases revision 10 or earlier opened get their assignment at the upgrade now.
- Fixed: a spec event could skip databases. The event walked the open databases with `next` while switching them, and a profile listener that opened databases during the switch added keys to the table being walked, which the Lua 5.1 manual leaves undefined: once the table grew, the walk skipped databases that should have switched (it may also raise `invalid key to 'next'`). The walk now only collects the databases to switch, into an array allocated only when there is one, and switches them afterwards.
- Implementation revision 12. No state changed: an upgrade over revision 11 keeps every database, assignment and the shared listener.
- Docs: `docs/API.md` lists the refusals revision 11 added under *Error behaviour*, names `GetSpecIndex` among the facade methods that refuse another receiver, and adds the spec step to *What `Open` does, in order*; the README gains the AceDB-3.0 migration table; the client suite's `EXPECTED.md` names the twenty-two database methods and `GetSpecIndex`.
- Specs: three more (`SpecProfiles_spec.lua`, 271 in all), each failing without its fix; the third opens 100 databases from the first switch of a spec event and requires all six databases with an assignment to switch once.

## 0.3.0 — 2026-09-25

A contract change inside API generation 1, approved by the owner, and a new opt-in read API, after the host benchmark against AceDB-3.0 (`docs/BENCHMARKS.md`).

- Changed: **views hold their saved tables.** Each view caches the saved table it resolved, stamped with a per-database generation that every SettingsKit mutation able to change it bumps: a write storing, replacing or removing a table or creating the tables on its path, `SetProfile` to a new profile, `CopyProfile`, `ResetProfile`, `DeleteProfile`, `ResetDatabase`, `Compact` (and the logout compaction) and `Resync`. A scalar written over a scalar bumps nothing. Nothing SettingsKit does is ever answered from a stale table, through detached views and in read-only databases too. The consequence: a **direct edit of the saved variable after `Open`** that adds, replaces or removes a table (or sets a metatable) is no longer seen by views that already hold their tables until the addon calls `db:Resync()`; a scalar edited inside a table a view holds still shows at once. A saved table with a metatable is never cached and is read with `rawget`.
- Added: `db:Resync()`: every view finds its saved table again on its next access. One field write; allowed on a read-only database.
- Added: `db:Getter(source, key)`, for hot loops: a function returning exactly what `view[key]` returns, where `source` is a view (read for good) or a scope name (whose current view it follows, the new profile after `SetProfile`). It skips the metamethod dispatch, the per-call `issecretvalue` probe of the key (the key is probed, and a secret, `nil` or NaN key refused, when the getter is made) and, for a plain-valued field, the choice of how to answer; it keeps defaults, wildcard defaults, mutation tracking, detached views and read-only databases exactly as views do, and keeps working across an in-place upgrade. A call allocates nothing.
- Reads through a cached table use plain indexing (a raw lookup, since a cached table has no metatable) instead of `rawget`.

## 0.2.0 — 2026-09-25

A contract change inside API generation 1 (nothing was released yet): migrations are transactional, data a newer version saved opens read-only, and two ways corrupted saved data could lock an addon out are closed.

- Fixed: a migration step that raised left the writes it made before the error in the saved table, and the next `Open` ran the step again over them (a step doubling `scale` turned 1 into 4 instead of 2). Each step now receives a deep copy of the saved table's current contents; when it returns, the copy's contents replace the saved table's contents in place (the saved-variable global keeps its identity) and the version is stored. When it raises, the saved table and its version are exactly as before the step, `Open` raises `SettingsKit:Open migration <step> of <name> failed: <error>` at the caller as before, the earlier steps stay committed, and the next `Open` retries only the failing step on untouched data. The copy preserves shared references and cycles (a reference to the table the step received becomes one to the saved table), keeps keys as they are, never invokes a metamethod and carries a secret over as it is. A step must not keep a reference to its table after it returns. Cost: one deep copy and one walk of the saved table per pending step, only while the stored version is behind; 10,000 nested profiles (about 50,000 tables) measured about 26 ms per step on host Lua 5.1.
- Changed: a stored version above `options.version` (a downgrade) opened the database fully writable, so an older addon version could change data a newer one wrote. Such a database now opens **read-only** by default: `Open` writes nothing (no layout section, profile table or profile choice, and the stored version is kept), reads work, and every write path raises at the writer's line naming the saved variable, the stored and requested versions and the opt-in — a write through any view (`SettingsKit (MyAddonDB) profile.frame is read-only: the saved table has version 9, newer than options.version 2; pass options.allowNewerData = true to SettingsKit:Open to write it`), `SetProfile`, `CopyProfile`, `ResetProfile`, `DeleteProfile`, `ResetDatabase` and `Compact` (`SettingsKit.Database:SetProfile cannot change MyAddonDB, which is read-only: ...`). `Validate` answers `false` with the view message, a plain-table default read is not stored, and the logout compaction skips the database.
- Added: `db:IsReadOnly()`, and the `Open` option `allowNewerData` (a boolean, requires `version`; a secret, a non-boolean and an unknown spelling are refused at the caller) that opens newer data writable as before. The stored version is never lowered, in either mode: `ResetDatabase` of such a database stamps the newer stored version.
- Fixed: a saved value that is not a table where the schema declares a record or keyed section (`profiles.Default.frame = 5`) was returned by the view, so `db.profile.frame.x` raised and an OptionsKit tree bound below it could not be read or reset. It now reads as absent (the default view, or `nil` without a default); a read never overwrites it and the next write through the view replaces it.
- Fixed: the layout was checked only after the migrations had run and stamped the version, so a saved table with a non-table section (`global = 5`) was changed and then refused on every `Open`. The layout is now checked before anything is written when no step with a function is pending, and on the result of the last such step before that result is committed (`SettingsKit:Open migration <step> of <name> failed: <name>.global must be a table`); earlier steps may still pass through any shape, so a step can restructure a pre-SettingsKit table, and a failed layout check can be fixed by a corrected migration that is retried on untouched data.
- Fixed: `Open` with `version` and without `migrations` over an older saved table raised `migration <n> ... failed: attempt to call a boolean value` instead of advancing the stored version.
- Implementation revision 5, database layout 2 (`_newerVersion`, `_readOnly`). An in-place upgrade over revisions 1 to 4 gives every database they opened both fields: it stays writable, as it was opened, and records a newer stored version so `ResetDatabase` never lowers it; databases opened afterwards follow the read-only rule.
- API.md: *Migrations* (transactions, the copy, cost), *Newer stored data: read-only databases*, the `Open` options table and order, `IsReadOnly`, the reads table, and the new messages under *Error behaviour*. INTERNALS.md: the database fields, *Migrations* and the revision 5 upgrade.
- 173 specs (143 before): `Migrations_spec.lua` (transactions, failure at every step, identity, shared references and cycles, no metamethod run, secrets, 10,000 profiles, the layout check), `ReadOnly_spec.lua` (every write path, reads, `Validate`, logout, `allowNewerData`, `IsReadOnly`, option validation), `CorruptedData_spec.lua`, and the upgrade over revision 4 in `Bootstrap_spec.lua`.
- Confirmed on the real client (Retail 12.1.0 b69933, 2026-09-25, 16:14): run 2 of `tests/client/MoltenCodesTest_SettingsKit` 39 passed, 1 skipped (the documented step one of run 2). The read-only refusals, the atomic retry (scale 2, not 4), `allowNewerData` and the scalar read as absent behave as the specs say, with the messages at the suite's calling lines.

## 0.1.0 — 2026-09-23

- Added SettingsKit API generation 1, implementation revision 1.
- Added `SettingsKit:Open(savedVariable, schema, options)`: one database per saved-variable name for the session; opening the name again returns the same database. A missing saved variable is created as `{}`; any other non-table value is refused. `schema` maps the scopes `global`, `char`, `realm`, `class`, `faction` and `profile` to SchemaKit `table` schemas, each sealed by SettingsKit; every field of a record read through a view must be `optional`. Options are `defaultProfile` (`"Default"`, `"char"` or a name), `version` and `migrations`; unknown fields are refused.
- Scope keys are read once at `Open` from `UnitName`, `GetRealmName`, `UnitClass` and `UnitFactionGroup`. A scope whose key is missing is unavailable, and reading it raises at the reading line; so does reading a scope the schema does not declare.
- Views: `db.<scope>` are empty proxies over the saved table. Reads fall back to the schema's defaults, including wildcard defaults for every key of a keyed section, without writing them back; plain table defaults (arrays) are copied into the saved table on first read. Writes are checked against the scope's schema at the writer's line with SchemaKit's failure text, keyed sections are held to their `max`, and secret keys and values (also nested in a table) are refused.
- Profiles: `GetProfile`, `SetProfile` (creates the profile and records the choice per character), `GetProfiles` (sorted), `CopyProfile`, `ResetProfile`, `DeleteProfile` (the current profile is refused; views of a deleted profile are detached) and `ResetDatabase`.
- Signals, each returning a SignalKit connection: `OnChange(scope, callback)` called with `(db, scope, key, value, path)` after every validated write, `OnProfileChanged`, `OnProfileCopied`, `OnProfileReset` and `OnProfileDeleted`.
- Versioned migrations: each `migrations[n]` receives the raw saved table and runs once, in ascending order, from the stored version + 1 to `options.version`, storing the version after each step. A new, empty saved table is stamped without running any.
- `db:Compact()` removes every saved value equal to its default across every character, realm, class, faction and profile entry, and returns how many it removed. With EventKit API 1 present (found through `Registry:Find`), every database compacts itself on `PLAYER_LOGOUT`; a failure there is reported, not raised.
- The saved table keeps a `namespaces` section and a `profileKeys` section from v1, so v2 (spec-aware profiles and namespaces) needs no layout change.
- A view assigned as a value, or a table carrying a metatable, is refused at the writer's line, top level or nested and on every client, so a saved table never aliases a view or skips validation.
- Reading a missing keyed-section entry never stores anything, so reads cannot grow a section past its `max` or store a key its key schema refuses; only a validated write creates an entry.
- Added `db:Pairs(view)`: a stateless, allocation-free iterator over a view's keys with defaults, then its saved keys.
- A record view refuses a secret read key, as a keyed-section view does.
- Added `db:Validate(scope, path, value)`: `true`, or `false` and the exact message a write would raise, running every check of a write (secret, view and metatable refusal, schema, keyed-section key and `max`) without writing. `path` is a dotted string or an array of keys; an array path allocates nothing for a valid value while the entry views on it are cached.
- The manifest lists EventKit API 1 under `optionalDependencies`.
- A default read and a validated write of an existing key allocate nothing. Databases, views and their listeners survive an in-place upgrade.
- A keyed-section read asks `issecretvalue` about the key before comparing it with `nil`, as a record read already did; comparing a secret raises in the client.
- Removed private state nothing read: the plan's `kind` field, the database's `_logoutConnection` field (EventKit holds the listener; a database is never disconnected) and the depth counter threaded through compaction (the plan already bounds the walk). A write's refusal prefix is built only for a refusal.
- API.md lists every use of `issecretvalue`, says a secret key refuses a read of any view, and qualifies the allocation of `db:Pairs` and of an array-path `Validate`.
- Keys in SettingsKit messages and in the `path` argument of `OnChange` listeners are rendered with SchemaKit's rule for failure paths: an identifier of at most 32 bytes is joined with a dot; any other string is quoted with `|` doubled, `\` and `"` escaped and other control bytes shown as `\ddd`, and cut at 32 bytes between UTF-8 characters. A key a hostile player sends can therefore not render client markup when a refusal is logged, and SettingsKit and SchemaKit show a key the same way.
- Limits, per principle 4a: `Open` accepts `maxScannedEntries` (default 65536, `SettingsKit.UNBOUNDED` allowed), the bound of the secret-value scan of a written table, kept per database. `SettingsKit:SetLimits` and `SettingsKit:GetLimits` over the session-shared `maxProfileNameLength` (default 64, from 64 to 1024) and `pathKeyLimit` (default 32, from 1 to 1024); neither accepts `UNBOUNDED`, and the refusal names the reason. `SettingsKit.UNBOUNDED` is one sentinel kept in the package state with the limits, so an upgrade keeps both. `MAX_PROFILE_NAME_LENGTH` stays the default. API.md gains a *Limits* section.
- The depth bound of every scan, comparison and `CopyProfile` is SchemaKit's `maxDepth` read through `SchemaKit:GetLimits()` when the walk starts, not `SchemaKit.MAX_DEPTH` copied at load, so `SchemaKit:SetLimits{ maxDepth }` reaches SettingsKit; views are built to the depth in force at `Open`.
- 130 specs, including allocation guards, an in-place upgrade spec, limit specs (the sentinel and set limits carried across an upgrade) and pinned error levels.
