# Changelog

## 0.3.0 — 2026-09-25

A contract change inside API generation 1, approved by the owner, and a new opt-in read API, after the host benchmark against AceDB-3.0 (`docs/BENCHMARKS.md`).

- Changed: **views hold their saved tables.** Each view caches the saved table it resolved, stamped with a per-database generation that every SettingsKit mutation able to change it bumps: a write storing, replacing or removing a table or creating the tables on its path, `SetProfile` to a new profile, `CopyProfile`, `ResetProfile`, `DeleteProfile`, `ResetDatabase`, `Compact` (and the logout compaction) and `Resync`. A scalar written over a scalar bumps nothing. Nothing SettingsKit does is ever answered from a stale table, through detached views and in read-only databases too. The consequence: a **direct edit of the saved variable after `Open`** that adds, replaces or removes a table (or sets a metatable) is no longer seen by views that already hold their tables until the addon calls `db:Resync()`; a scalar edited inside a table a view holds still shows at once. A saved table with a metatable is never cached and is read with `rawget`.
- Added: `db:Resync()`: every view finds its saved table again on its next access. One field write; allowed on a read-only database.
- Added: `db:Getter(source, key)`, for hot loops: a function returning exactly what `view[key]` returns, where `source` is a view (read for good) or a scope name (whose current view it follows, the new profile after `SetProfile`). It skips the metamethod dispatch, the per-call `issecretvalue` probe of the key (the key is probed, and a secret, `nil` or NaN key refused, when the getter is made) and, for a plain-valued field, the choice of how to answer; it keeps defaults, wildcard defaults, mutation tracking, detached views and read-only databases exactly as views do, and keeps working across an in-place upgrade. A call allocates nothing.
- Reads through a cached table use plain indexing (a raw lookup, since a cached table has no metatable) instead of `rawget`.

## 0.2.1 — 2026-09-25

Internal speed-ups after the host benchmark against AceDB-3.0 (`docs/BENCHMARKS.md`). No documented behaviour changes: every check, refusal, message, error level, default, signal and limit is as in 0.2.0.

Measured with `python3 -m tooling.bench.run --workload settings --rounds 3`, host Lua 5.1 on a shared machine with other benchmarks running (load average about 6 during the before run, 2 to 3 during the after run), so compare the ratios and bytes. The absolute times of the three rows AceDB has no counterpart for come from running both revisions back to back in one sitting, the same operation on the same schema:

| Case | 0.2.0 (revision 5) | 0.2.1 (revision 6) |
|---|---|---|
| `open-empty` | 23.7× AceDB, 35,434 B | 4.4× AceDB, 7,235 B |
| `open-populated` | 12.1× AceDB, 34,842 B | 2.4× AceDB, 6,640 B |
| held per open database | 25,538 B | 6,168 B (AceDB 3,872 B) |
| `switch-profile` | 0.37× AceDB, 0 B | 0.28× AceDB, 0 B |
| `read-default` | 84× AceDB | 58× AceDB |
| `read-saved` | 78× AceDB | 58× AceDB |
| `read-nested` | 110× AceDB | 69× AceDB |
| `read-entry-default` | 108× AceDB | 71× AceDB |
| `write-scalar` (not compared) | 1,601 ns | 466 ns |
| `write-nested` (not compared) | 2,199 ns | 1,051 ns |
| `validate` (SettingsKit only) | 2,553 ns | 1,377 ns |

- **Open.** The seal, description and plan of a scope schema are compiled once per schema node and reused by every later `Open` with it, while SchemaKit's `maxDepth` and revision stay the same. The change and profile signals are created by the first listener, the messages for undeclared and unavailable scopes when such a scope is read, and every database shares one `PLAYER_LOGOUT` listener instead of connecting its own (compaction order and failure isolation unchanged). View nodes hold at most 16 fields, so each takes a 16-slot table instead of a 32-slot one.
- **Reads.** A record read is answered inside the view's `__index` from read kinds worked out when the view was built, so it tests the type of no default; the saved table is still resolved on every read, one `rawget` and one `type` per level, now without a call per level. What remains against AceDB's plain table read is what the contract requires: the metamethod call of an empty proxy (validated writes need one), the `issecretvalue` probe of the key, and the resolution that keeps views valid over emptied or replaced saved tables.
- **Writes and `Validate`.** A value that is not a table, written to a declared `string`, `number`, `boolean` or `enum` field through a view that already passed a full check, is checked by SettingsKit against the field's rules as `schema:Describe()` states them, and below the top level against SchemaKit's current `maxDepth` through one small SchemaKit check, instead of a SchemaKit check of the whole probe chain. Anything else, and every refusal, still runs SchemaKit's check, so verdicts and messages are SchemaKit's. A write nobody listens to fires no signal.
- Implementation revision 6: node layout 2, plan layout 2, database layout 3 (no `_unavailable`) and the shared logout list in the package state. An in-place upgrade over revisions 1 to 5 brings every database, scope plan and live view to these layouts; a database an older revision opened keeps its own logout listener and is compacted once. API generation 1 is unchanged.
- API.md: the performance table (measured costs, when a write takes the fast path, the compiled schema reused), the shared seal, the shared logout listener, revision 6 under *Embedded copies and upgrades*. INTERNALS.md: package state, databases, plans (the compiled-schema and read-kind caches), nodes, resolution, a read, a write (the fast path and the depth probes), the logout listener and the revision 6 upgrade.
- 197 specs (173 before): `FastPaths_spec.lua` (every candidate value against every kind of scalar field, before and after verification, at three depths, with SchemaKit's verdict and message each time; a lowered `maxDepth`; refused keys, full sections, detached views and secrets after verification; read kinds; shared compiled schemas; signals created on demand; the shared logout compaction), four allocation guards, and the upgrade over revision 5 in `Bootstrap_spec.lua`.

## 0.2.0 — 2026-09-25

A contract change inside API generation 1 (nothing was released yet): migrations are transactional, data a newer version saved opens read-only, and two ways corrupted saved data could lock an addon out are closed.

- Fixed: a migration step that raised left the writes it made before the error in the saved table, and the next `Open` ran the step again over them (a step doubling `scale` turned 1 into 4 instead of 2). Each step now receives a deep copy of the saved table's current contents; when it returns, the copy's contents replace the saved table's contents in place (the saved-variable global keeps its identity) and the version is stored. When it raises, the saved table and its version are exactly as before the step, `Open` raises `SettingsKit:Open migration <step> of <name> failed: <error>` at the caller as before, the earlier steps stay committed, and the next `Open` retries only the failing step on untouched data. The copy preserves shared references and cycles (a reference to the table the step received becomes one to the saved table), keeps keys as they are, never invokes a metamethod and carries a secret over as it is. A step must not keep a reference to its table after it returns. Cost: one deep copy and one walk of the saved table per pending step, only while the stored version is behind; 10,000 nested profiles (about 50,000 tables) measured about 26 ms per step on host Lua 5.1.
- Changed: a stored version above `options.version` (a downgrade) opened the database fully writable, so an older addon version could change data a newer one wrote. Such a database now opens **read-only** by default: `Open` writes nothing (no layout section, profile table or profile choice, and the stored version is kept), reads work, and every write path raises at the writer's line naming the saved variable, the stored and requested versions and the opt-in — a write through any view (`SettingsKit (MyAddonDB) profile.frame is read-only: the saved table has version 9, newer than options.version 2; pass options.allowNewerData = true to SettingsKit:Open to write it`), `SetProfile`, `CopyProfile`, `ResetProfile`, `DeleteProfile`, `ResetDatabase` and `Compact` (`SettingsKit.Database:SetProfile cannot change MyAddonDB, which is read-only: ...`). `Validate` answers `false` with the view message, a plain-table default read is not stored, and the logout compaction skips the database.
- Added: `db:IsReadOnly()`, and the `Open` option `allowNewerData` (a boolean, requires `version`; a secret, a non-boolean and an unknown spelling are refused at the caller) that opens newer data writable as before. The stored version is never lowered, in either mode: `ResetDatabase` of such a database stamps the newer stored version.
- Fixed: a saved value that is not a table where the schema declares a record or keyed section (`profiles.Default.frame = 5`) was returned by the view, so `db.profile.frame.x` raised and an OptionsKit tree bound below it could not be read or reset. It now reads as absent (the default view, or `nil` without a default); a read never overwrites it and the next write through the view replaces it.
- Fixed: the layout was checked only after the migrations had run and stamped the version, so a saved table with a non-table section (`global = 5`) was changed and then refused on every `Open`. The layout is now checked before anything is written when no step with a function is pending, and on the result of the last such step before that result is committed (`SettingsKit:Open migration <step> of <name> failed: <name>.global must be a table`); earlier steps may still pass through any shape, so a step can restructure a pre-SettingsKit table, and a failed layout check can be fixed by a corrected migration that is retried on untouched data.
- Fixed: `Open` with `version` and without `migrations` over an older saved table raised `migration <n> ... failed: attempt to call a boolean value` instead of advancing the stored version.
- Implementation revision 5, database layout 2 (`_newerVersion`, `_readOnly`). An in-place upgrade over revisions 1 to 4 gives every database they opened both fields: it stays writable, as it was opened, and records a newer stored version so `ResetDatabase` never lowers it; databases opened afterwards follow the read-only rule.
- API.md: *Migrations* (transactions, the copy, cost), *Newer stored data: read-only databases*, the `Open` options table and order, `IsReadOnly`, the reads table, and the new messages under *Error behaviour*. INTERNALS.md: the database fields, *Migrations* and the revision 5 upgrade.
- 173 specs (143 before): `Migrations_spec.lua` (transactions, failure at every step, identity, shared references and cycles, no metamethod run, secrets, 10,000 profiles, the layout check), `ReadOnly_spec.lua` (every write path, reads, `Validate`, logout, `allowNewerData`, `IsReadOnly`, option validation), `CorruptedData_spec.lua`, and the upgrade over revision 4 in `Bootstrap_spec.lua`.
- Confirmed on the real client (Retail 12.1.0 b69933, 2026-09-25, 16:14): run 2 of `tests/client/MoltenCodesTest_SettingsKit` 39 passed, 1 skipped (the documented step one of run 2). The read-only refusals, the atomic retry (scale 2, not 4), `allowNewerData` and the scalar read as absent behave as the specs say, with the messages at the suite's calling lines.

## 0.1.4 — 2026-09-24

- Audit of 2026-09-24 against the Retail 12.1.0 b69933 finding that testing a secret as a boolean raises: SettingsKit tests no value it did not create as a boolean. The audit found two places where a secret caller value was used as a table key, which raises inside SettingsKit: a secret scope name passed to `db:OnChange` or `db:Validate` is now refused at the caller's line (`SettingsKit.Database:OnChange scope must not be a secret value`, likewise for `Validate`), and reading a database with a secret key (`db[key]`) raises `SettingsKit databases cannot be read with a secret key` at the reading line. Both are documented under "Error behaviour" in `docs/API.md`.
- Implementation revision 4. No state changed: the database metatable's `__index` is rewritten in place, so an in-place upgrade from revision 3 gives its databases the new refusal at once.
- Specs: `Writes_spec.lua` covers both refusals; `Bootstrap_spec.lua` upgrades revision 3 in place. `SettingsKit` API generation 1 is unchanged.

## 0.1.3 — 2026-09-24

- Secret values: API.md (error behaviour), INTERNALS.md (absent values), the source comments on `maxScannedEntries`, value equality and `readMap`, and a spec comment no longer claim that comparing a secret with anything, `nil` included, raises, or that a raw identity test is safe whatever the other side. They state what was measured on Retail 12.1.0 b69933 (2026-09-24): a secret compared with a value of its own type raises (`==`, `~=`, `<`, `<=` and `rawequal` alike) and a secret used as a table key raises, while a comparison with `nil` or with a value of another type answers without raising. The `type(value) == "nil"` rule stays, as the repository's uniform rule that never compares anything. Comments and documentation only: `luac -s -l` gives the same instruction listing before and after, so the implementation revision is unchanged.

## 0.1.2 — 2026-09-24

- Fixed: values that do not originate in SettingsKit were compared with `nil`, which raises on a client with secret values. Arguments, option and limit fields, saved-variable entries (values and keys, including `next` on a saved table), migration functions and schema defaults are now tested with `type(value) == "nil"`, so a secret stored in a saved table is read back, iterated and compacted without a comparison.
- Fixed: `Open` compared `options.maxScannedEntries` with `SettingsKit.UNBOUNDED` and `options.version` and the `migrations` keys with numbers before asking `issecretvalue`; each is now refused at the caller first (`SettingsKit:Open options.maxScannedEntries must not be a secret value`, `SettingsKit:Open options.version must not be a secret value`, `SettingsKit:Open options.migrations must not have a secret key`). A secret option name is reported as `"<secret>"` instead of indexing the known names with it.
- Fixed: `SetLimits` indexed the known limits with the key and compared the value with `SettingsKit.UNBOUNDED` before asking `issecretvalue`; a secret key or value is now refused at the caller (`SettingsKit:SetLimits limits must not have a secret key`, `SettingsKit:SetLimits limits.<name> must not be a secret value`).
- Fixed: `DeleteProfile` compared every stored profile choice with the deleted name; a secret choice is skipped, as `Open` already ignores it. A secret stored `version` is refused as a non-integer instead of being compared, and a reopening `Open` tests the schema argument's type before comparing it with the first schema.
- Implementation revision 3. The state schema and every layout are unchanged; an upgrade over revision 2 keeps databases, views and listeners and applies the new checks at once.
- API.md lists the new refusals under *Error behaviour*; INTERNALS.md states which values are tested with `type`.

## 0.1.1 — 2026-09-24

- Fixed: a saved entry of a keyed section declared without a default of its own (`auras = S.optional(S.map{ ... })`) read `nil` for every field it did not store, instead of the wildcard default and the record's field defaults, and so did the records below it; `db:Pairs` skipped those defaults too. `Compact` compared the same entry with the wildcard, so it could remove a value that then read back as `nil`. An entry view now reads the section's own default entry, else the wildcard default, else the record's field defaults, whether or not the section has a default.

## 0.1.0 — 2026-09-23

- Added SettingsKit API generation 1, implementation revision 1.
- Added `SettingsKit:Open(savedVariable, schema, options)`: one database per saved-variable name for the session; opening the name again returns the same database. A missing saved variable is created as `{}`; any other non-table value is refused. `schema` maps the scopes `global`, `char`, `realm`, `class`, `faction` and `profile` to SchemaKit `table` schemas, each sealed by SettingsKit; every field of a record read through a view must be `optional`. Options are `defaultProfile` (`"Default"`, `"char"` or a name), `version` and `migrations`; unknown fields are refused.
- Scope keys are read once at `Open` from `UnitName`, `GetRealmName`, `UnitClass` and `UnitFactionGroup`. A scope whose key is missing is unavailable, and reading it raises at the reading line; so does reading a scope the schema does not declare.
- Views: `db.<scope>` are empty proxies over the saved table. Reads fall back to the schema's defaults, including wildcard defaults for every key of a keyed section, without writing them back; plain table defaults (arrays) are copied into the saved table on first read. Writes are checked against the scope's schema at the writer's line with SchemaKit's failure text, keyed sections are held to their `max`, and secret keys and values (also nested in a table) are refused.
- Profiles: `GetProfile`, `SetProfile` (creates the profile and records the choice per character), `GetProfiles` (sorted), `CopyProfile`, `ResetProfile`, `DeleteProfile` (the current profile is refused; views of a deleted profile are detached) and `ResetDatabase`.
- Signals, each returning a SignalKit connection: `OnChange(scope, callback)` called with `(db, scope, key, value, path)` after every validated write, `OnProfileChanged`, `OnProfileCopied`, `OnProfileReset` and `OnProfileDeleted`.
- Versioned migrations: each `migrations[n]` receives the raw saved table and runs once, in ascending order, from the stored version + 1 to `options.version`, storing the version after each step. A new, empty saved table is stamped without running any.
- `db:Compact()` removes every saved value equal to its default across every character, realm, class, faction and profile entry, and returns how many it removed. With EventKit API 1 present (found through `Registry:Find`), every database compacts itself on `PLAYER_LOGOUT`; a failure there is reported, not raised.
- The saved table keeps a `namespaces` section and a `profileKeys` section from v1, so v2 (spec-aware profiles and namespaces) needs no layout change.
- A view assigned as a value, or a table carrying a metatable, is refused at the writer's line, top level or nested and on every client, so a saved table never aliases a view or skips validation.
- Reading a missing keyed-section entry never stores anything, so reads cannot grow a section past its `max` or store a key its key schema refuses; only a validated write creates an entry.
- Added `db:Pairs(view)`: a stateless, allocation-free iterator over a view's keys with defaults, then its saved keys.
- A record view refuses a secret read key, as a keyed-section view does.
- Added `db:Validate(scope, path, value)`: `true`, or `false` and the exact message a write would raise, running every check of a write (secret, view and metatable refusal, schema, keyed-section key and `max`) without writing. `path` is a dotted string or an array of keys; an array path allocates nothing for a valid value while the entry views on it are cached.
- The manifest lists EventKit API 1 under `optionalDependencies`.
- A default read and a validated write of an existing key allocate nothing. Databases, views and their listeners survive an in-place upgrade.
- A keyed-section read asks `issecretvalue` about the key before comparing it with `nil`, as a record read already did; comparing a secret raises in the client.
- Removed private state nothing read: the plan's `kind` field, the database's `_logoutConnection` field (EventKit holds the listener; a database is never disconnected) and the depth counter threaded through compaction (the plan already bounds the walk). A write's refusal prefix is built only for a refusal.
- API.md lists every use of `issecretvalue`, says a secret key refuses a read of any view, and qualifies the allocation of `db:Pairs` and of an array-path `Validate`.
- Keys in SettingsKit messages and in the `path` argument of `OnChange` listeners are rendered with SchemaKit's rule for failure paths: an identifier of at most 32 bytes is joined with a dot; any other string is quoted with `|` doubled, `\` and `"` escaped and other control bytes shown as `\ddd`, and cut at 32 bytes between UTF-8 characters. A key a hostile player sends can therefore not render client markup when a refusal is logged, and SettingsKit and SchemaKit show a key the same way.
- Limits, per principle 4a: `Open` accepts `maxScannedEntries` (default 65536, `SettingsKit.UNBOUNDED` allowed), the bound of the secret-value scan of a written table, kept per database. `SettingsKit:SetLimits` and `SettingsKit:GetLimits` over the session-shared `maxProfileNameLength` (default 64, from 64 to 1024) and `pathKeyLimit` (default 32, from 1 to 1024); neither accepts `UNBOUNDED`, and the refusal names the reason. `SettingsKit.UNBOUNDED` is one sentinel kept in the package state with the limits, so an upgrade keeps both. `MAX_PROFILE_NAME_LENGTH` stays the default. API.md gains a *Limits* section.
- The depth bound of every scan, comparison and `CopyProfile` is SchemaKit's `maxDepth` read through `SchemaKit:GetLimits()` when the walk starts, not `SchemaKit.MAX_DEPTH` copied at load, so `SchemaKit:SetLimits{ maxDepth }` reaches SettingsKit; views are built to the depth in force at `Open`.
- 130 specs, including allocation guards, an in-place upgrade spec, limit specs (the sentinel and set limits carried across an upgrade) and pinned error levels.
